### Bronze — Staging Views (`bronze_dbt` schema)

All bronze models are thin passthroughs — no column renaming, no casting, no filtering.

### Silver — Dimensions (`silver` schema)

**`dim_security`** — 1 row / sec_id  
Columns: `sec_id`, `ticker`, `asset_class`, `sector`, `maturity`, `issue_date`, `rating`, `latest_rating_agency`, `latest_rating_date`  
Note: SPY/AGG are re-classified to `asset_class = 'Benchmark'`; rating resolves from latest stg_ratings row, falling back to security master.

**`dim_portfolio`** — 1 row / portfolio_id  
Columns: `portfolio_id` (derived via `SELECT DISTINCT` from stg_positions)

**`dim_benchmark`** — 1 row / benchmark_id  
Columns: `benchmark_id` (derived via `SELECT DISTINCT` from stg_benchmarks)

**`dim_date`** — 1 row / date_day (full calendar spine including weekends)  
Columns: `date_day`, `year`, `quarter`, `month`, `week_of_year`, `day_of_week`, `month_name`, `is_weekend`  
Spine covers min(position_date, price_date) → max(position_date, price_date).

### Silver — Facts (`silver` schema)

**`fct_position_daily`** — grain: portfolio_id × sec_id × position_date  
Columns: `portfolio_id`, `sec_id`, `position_date`, `market_value`, `par_value`, `weight`, `asset_class`, `sector`, `rating`, `year`, `quarter`, `month`

**`fct_price_daily`** — grain: sec_id × price_date  
Columns: `sec_id`, `price_date`, `price`, `source`, `asset_class`, `sector`, `year`, `quarter`, `month`

**`fct_benchmark_return_daily`** — grain: benchmark_id × benchmark_date  
Columns: `benchmark_id`, `benchmark_date`, `return`, `year`, `quarter`, `month`

### Marts (`marts` schema)

**`mart_portfolio_exposure`** — 1 row / portfolio_id  
Columns: `portfolio_id`, `position_date`, `total_nav`, `top10_mv`, `top10_concentration_pct`, `asset_class_breakdown` (JSON), `sector_breakdown` (JSON)

**`mart_credit_exposure`** — 1 row / portfolio_id × rating_bucket  
Columns: `portfolio_id`, `position_date`, `rating_bucket`, `market_value`, `pct_of_fixed_income`, `pct_of_total_nav`

**`mart_duration_summary`** — 1 row / portfolio_id  
Columns: `portfolio_id`, `position_date`, `fi_nav`, `weighted_avg_duration`

**`mart_var_parametric`** — 1 row / portfolio_id  
Columns: `portfolio_id`, `position_date`, `nav`, `sigma_daily`, `var_95_1d`, `var_99_1d`

**`mart_tracking_error`** — 1 row / portfolio_id × benchmark_id  
Columns: `portfolio_id`, `benchmark_id`, `te_30d`, `te_60d`, `te_90d`

**`mart_scenario_impact`** — 1 row / portfolio_id × scenario_id  
Columns: `portfolio_id`, `scenario_id`, `factor`, `shock_pct`, `position_date`, `mv_change_usd`, `mv_change_pct`

**`mart_concentration_limits`** — 1 row / portfolio_id × sec_id  
Columns: `portfolio_id`, `position_date`, `sec_id`, `ticker`, `weight_pct`, `breach_flag`, `breach_amount_over_5pct`

### Recon (`recon` schema)

**`recon_position_to_nav`** — 1 row / portfolio_id  
Columns: `portfolio_id`, `position_date`, `sum_mv`, `declared_nav`, `variance_pct`, `status`

**`recon_benchmark_coverage`** — 1 row / benchmark_id  
Columns: `benchmark_id`, `benchmark_date`, `expected_constituents`, `priced_constituents`, `coverage_pct`, `status`

**`recon_stale_prices`** — 1 row / sec_id  
Columns: `sec_id`, `ticker`, `last_price_date`, `days_since`, `status`

**`recon_rating_coverage`** — 1 row / sec_id (FI only)  
Columns: `sec_id`, `ticker`, `has_rating`, `status`

### Type 2 / SCD Patterns

**None found.** No model uses `valid_from`, `valid_to`, `effective_from`, `effective_to`, `is_current`, or `scd_type:2` patterns. The `dim_security` rating resolution uses `DISTINCT ON (sec_id) ORDER BY rating_date DESC` — effectively a Type 1 (latest-wins) overwrite, not a Type 2 history preservation.

## 3. Reconciliation

### Framework Present: **Yes**

Four reconciliation models exist in `models/recon/`, materialized as tables in the `recon` schema.

### What It Reconciles

| Gate | Reconciles | Layers |
|---|---|---|
| `recon_position_to_nav` | Sum of position market values vs declared NAV targets | Bronze (stg_positions) → declared constants |
| `recon_benchmark_coverage` | Benchmark constituent price coverage on latest benchmark date | Bronze (stg_benchmarks, stg_prices) → cross-check |
| `recon_stale_prices` | Days since last price per security vs current date | Bronze (stg_prices) → current_date |
| `recon_rating_coverage` | Fixed income securities with at least one rating record | Bronze (stg_security_master, stg_ratings) → coverage check |

### Output Location

All four recon models materialize as **tables** in the PostgreSQL `recon` schema. No file or view outputs; outputs are queryable tables.

### Latest Variance Numbers

No reconciliation summary file (CSV, JSON, etc.) was found in the repository. The recon output lives entirely in the database. Based on code inspection:

- `recon_position_to_nav`: Declared NAVs are hardcoded — PORT_CORE = $100,000,000; PORT_FLEX = $50,000,000. Pass threshold is ±0.1%.
- `recon_stale_prices`: As of 2026-05-06 (today), prices last ingested ~2026-05-04 would show `days_since = 2` → **PASS**. By 2026-05-09, bonds would show `days_since = 5` → **WARN**.
- `recon_rating_coverage` and `recon_benchmark_coverage`: These passed on the last recorded dbt test run.

No variance numbers can be reported without running a query.

### Items That Look Out of Place / Notable Findings

1. **`logs/dbt.log` is committed.** The `.gitignore` lists `logs/` as ignored, but this file is present in the working tree and was tracked at some point. The log is large (57,000+ lines) and contains local machine paths (`/Volumes/MacMini DB/...`, `/Volumes/MacMini Dock SSD/Users/nickhidalgo/...`), PostgreSQL connection details (host, port, username), and full dbt execution traces. It is benign (no credentials), but it should not be in a public repo.

2. **`.claude/settings.local.json` is committed.** Contains Claude Code project-level settings. The `.claude/` directory is not gitignored.

3. **`dbt_project.yml` warns on unused config path.** The log shows: `Configuration paths exist in your dbt_project.yml file which do not apply to any resources. There are 1 unused configuration paths: models.investment_risk_mart.marts`. The `marts` config block in `dbt_project.yml` uses `+schema: marts`, but no model in the `models/marts/` directory picks this up — they appear to be rendering into a schema prefixed with the dbt profile target schema (e.g., `silver_marts`). This is a minor schema-naming misconfiguration that does not block functionality but produces a warning on every run.

4. **`dim_portfolio` and `dim_benchmark` are very thin.** Both are single-column `SELECT DISTINCT` tables with no additional attributes. This is valid for a v0.1.0 but would be enriched in production (portfolio names, AUM, mandate type, etc.).

5. **No bronze-level schema.yml.** The `models/bronze/` directory has no `schema.yml`, meaning no dbt tests are defined on the staging views. Source-level freshness tests (`warn_after`, `error_after`) are defined in `sources.yml`, but column-level tests on the bronze views are absent. This is a common pattern but means raw data quality is not validated at the staging layer.

6. **`dashboard/assets/hero-shuttle-launch.jpg` is a binary asset committed to git.** At ~?KB this is fine for a static site, but binary files in git are generally better managed via LFS or CDN for larger projects. No issue at current size.

7. **`recon_stale_prices` uses calendar days, not business days.** This is documented in DATA_CONTRACT.md, but it means the gate will return WARN/FAIL on Monday/Tuesday after a normal weekend, even though no business-day price is missing. This is a known design choice with potential for false-positive operational noise.

8. **`declared_nav` values in `recon_position_to_nav` are hardcoded constants** in the SQL (`$100M` for PORT_CORE, `$50M` for PORT_FLEX) rather than driven from a reference table. This will require a SQL edit to change target NAVs.
